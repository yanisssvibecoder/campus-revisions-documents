analogy

Si l’adresse de ton ami est recopiée sur vingt fiches de jeux, son déménagement t’oblige à corriger vingt endroits. Garder une fiche personne puis la référencer évite vingt versions différentes.

explanation

  1. Troisième forme normale (3FN) dans le cadre introductif du cours : être en 2 FN et faire dépendre les attributs non clés directement de la clé, sans passer par un autre attribut non clé. Le raisonnement complet repose sur les dépendances fonctionnelles et les clés candidates.

  2. Exemple : noCommande→noClient et noClient→adresseClient. L’adresse dépend transitivement de la commande via le client. Dans Commande, garder la référence noClient ; dans Client, garder son adresse, sous réserve du besoin d’adresse historique de livraison.

  3. Anomalie de mise à jour : l’adresse est changée dans une seule ligne. Anomalie d’insertion : impossible d’enregistrer un nouveau client sans commande. Anomalie de suppression : supprimer sa dernière commande efface aussi son unique information client.

  4. La décomposition réduit ces risques et permet la réutilisation des données. Une référence repeated n’est pas une mauvaise redondance : elle relie les tables. Le modèle doit pouvoir reconstituer les informations sans associations parasites.

  5. Le contexte peut exiger un historique. L’adresse actuelle du client et l’adresse utilisée pour une livraison passée ne sont pas le même fait. Stocker les deux peut être légitime si leurs définitions et leur gestion sont explicites.

  6. Procédure : inventorier les champs ; déterminer clés/dépendances ; vérifier 1 FN ; retirer dépendances partielles ; retirer transitives ; tracer le DSBD ; vérifier chaque règle d’affaires avec des exemples valides et invalides.

vocabulary

  1. term

    Dépendance transitive

    meaning

    Dépendance de la clé vers un attribut en passant par un autre attribut non clé.

  2. term

    Anomalie d’insertion

    meaning

    Structure qui empêche d’ajouter un fait sans en créer un autre.

  3. term

    Anomalie de suppression

    meaning

    Suppression involontaire d’un fait en effaçant un autre.

  4. term

    DSBD

    meaning

    Schéma logique de la base avec tables, clés et liens.

  5. term

    Historique

    meaning

    Faits conservés tels qu’ils étaient au moment d’un événement.

formulas

    workedExamples

    1. title

      Adresse répétée — exemple original

      prompt

      Commande(noCommande, noClient, nomClient, adresseClient, dateCommande). Règle : noClient détermine nom et adresse actuelle.

      steps

      1. noCommande identifie la commande.

      2. noClient est non clé dans Commande et détermine nom/adresse.

      3. CréerClient(noClient, nom, adresse) ; Commande(noCommande, noClient, date).

      4. Relier Commande au Client existant.

      answer

      La donnée client n’est mise à jour qu’au bon endroit.

      pitfall

      Supprimer noClient avec nom/adresse et casser toute relation.

    2. title

      Une adresse historique différente — exemple original

      prompt

      Client 12 déménage après commande 100. Doit-on changer automatiquement le lieu livré de commande 100 ?

      steps

      1. AdresseClientActuelle décrit le client aujourd’hui.

      2. AdresseLivraisonDeCommande décrit le lieu convenu pour cet événement.

      3. Définir deux attributs/faits distincts, éventuellement avec une entitéAdresse et historique.

      4. La normalisation doit respecter la sémantique du cas, pas effacer l’histoire.

      answer

      Conserver le lieu de la transaction si le besoin historique existe.

      pitfall

      Penser que deux adresses sont forcément une erreur de normalisation.

    questions

    1. type

      mcq

      prompt

      noCommande→noClient→nomClient révèle…

      options

      1. une absence de données

      2. une dépendance transitive

      3. un champ atomique nécessairement invalide

      4. un algorithme

      correctIndex

      1

      solution

      nomClient dépend de la commande via un autre attribut ; créer l’entitéClient.

      id

      technologies-normalisation-3-q1

    2. type

      open

      prompt

      Une table ne permet pas d’ajouter un client sans vente. Quel problème et quelle correction ?

      solution

      Anomalie d’insertion ; séparer Client de Vente/Commande pour enregistrer le client indépendamment et référencer ensuite ce client dans ses transactions.

      rubric

      1. Nommer insertion.

      2. Créer entitéClient.

      3. Décrire le lien des transactions.

      id

      technologies-normalisation-3-q2

    3. type

      open

      prompt

      Dessine de mémoire le DSBD Client, Commande, Article, Detail.

      solution

      ClientPK noClient ; CommandePK noCommande et FK noClient ; ArticlePK noArticle ; DetailPK selon règle et FK noCommande/noArticle, quantité et prix vendu si exigé.

      rubric

      1. PK par table.

      2. FK côté plusieurs.

      3. Table d’association.

      4. Attributs du lien corrects.

      id

      technologies-normalisation-3-q3

    4. type

      open

      prompt

      Table Commande(noCommande, noClient, nomClient). Quel risque et quelle décomposition ?

      solution

      nomClient dépend de noClient, non directement de l’identité de commande. Créer Client(noClient, nomClient) et conserver noClient comme référence de Commande, selon les règles d’historique. Évite plusieurs versions contradictoires du nom.

      rubric

      1. Dépendance transitive.

      2. Client séparé.

      3. FK en Commande.

      4. Anomalie ou historique expliqué.

      id

      technologies-normalisation-3-q4
